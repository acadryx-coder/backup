ACADRYX — Multi-Tenant School Management Platform
Project Details


OVERVIEW

Acadryx is a progressive web application I designed and built as a multi-tenant school management system — a single deployment that serves many schools, rather than one codebase per client. A school is resolved at runtime from a subdomain (schoolname.acadryx.com) or a query parameter, and the app then loads that school's branding, active feature set, and data before rendering anything. Within each school, Acadryx serves five distinct user roles — admin, teacher, student, parent, and alumni — each with its own dashboard, permissions, and navigation, all from one shared codebase and one shared Postgres database (isolated by schema and Row Level Security).

The problem it solves is the fragmentation schools typically deal with: attendance on paper or in spreadsheets, grading in one system, fees tracked in another, and no shared line of communication between teachers, parents, and administrators. Acadryx consolidates all of it — school structure, grading and assessments, computer-based testing, attendance, finance, and communication — into one role-aware platform, configurable per school through a feature marketplace so that not every school needs every module active.


ROLE & CONTRIBUTIONS

I was the sole developer on Acadryx: architecture, database schema and RPC logic, every UI surface across all five portals, the design system, third-party integrations, and deployment. Specifically, I:

- Designed the multi-tenant slug-detection and bootstrap flow that resolves a school, its branding, and (if applicable) an already-logged-in user's session in a single upfront request, before any UI renders.
- Built out five role-based portal trees — admin, teacher, student, parent, alumni — comprising well over 100 routes, each gated by role checks and, for admin, by granular permission flags.
- Designed a custom, passwordless authentication scheme using per-user access codes, including a one-time "acknowledge and save your code" flow so new users can't lose access before writing their code down.
- Built a feature-flag ("feature marketplace") system so individual schools can have different modules turned on or off, threaded through every page via an activeFeatures set.
- Built the full admin configuration surface: school structure (sections, classes, class arms with drag-and-drop reordering), staff/student/parent/alumni management with bulk creation and login-code issuance, teacher-to-subject and teacher-to-class assignment matrices, timetable templates and per-arm editors, grading scales, weighted assessments, and a "freeze" mechanism to lock configuration during active score entry.
- Built the score-entry-to-publish pipeline: teacher score entry with a local-state diffing model (so only changed scores are saved) and an unsaved-changes browser warning, admin bulk preview/editing, one-click section-wide publishing, and a PDF result-card generator.
- Designed the PDF template system as a factory that currently produces state-specific templates for all 36 Nigerian states plus separate national templates for Ghana, Kenya, and other supported countries, sharing a common rendering pipeline to avoid duplicating layout code per region.
- Built the Computer-Based Testing (CBT) module end to end: question banks and pools, exam creation with configurable time limits and shuffle options, PIN-based student enrollment, a standalone timed exam-taking session (auto-submitting on timeout) that runs completely outside the main authenticated app shell, and server-side grading via RPC.
- Integrated Flutterwave for wallet-based billing, including a term-transition flow that blocks the transition and prompts a top-up when a school's wallet balance is insufficient.
- Carried the codebase through a mid-project restructuring: legacy admin/teacher modules and their "_new" replacements currently run side by side (both are still routed), and several modules and shared components have been incrementally migrated from JavaScript to TypeScript rather than rewritten in one pass.
- Wrote component-level tests (Jest + React Testing Library) with a mocked Supabase client for critical flows such as login.


TECHNICAL STACK

- Frontend: React 18, React Router DOM v7, Vite 5
- Backend/Data: Supabase (PostgreSQL), with the schema split across four Postgres schemas — schools, features, acadryx, and school_ops — plus Row Level Security, accessed via the Supabase JS client and Postgres RPC functions for multi-step, transactional operations
- Authentication: Custom, code-based login tokens (no passwords), with role and permission data resolved per profile at login
- Payments: Flutterwave (flutterwave-react-v3) for wallet top-ups
- PDF Generation: jsPDF + jspdf-autotable + html2canvas, with a factory-pattern template system for country/state-specific result cards
- Styling: Inline CSS-in-JS with a global CSS custom-property design system (a "Royal Blue & Gold" brand theme), no CSS framework
- Language mix: predominantly JavaScript (.jsx), with TypeScript (.tsx) adopted for newer modules — the login page, the rebuilt teacher portal, and several shared components — reflecting an incremental JS-to-TS migration rather than a rewrite
- Testing: Jest, Babel, @testing-library/react, @testing-library/user-event
- Tooling: ESLint (with TypeScript and React plugins), Prettier
- Deployment: Vercel (with an SPA rewrite rule) for the frontend, Supabase for the backend
- PWA: web app manifest and Apple touch icons configured for installability

Student Portal

Parent Portal

Results & Documents

Payments

TECHNICAL CHALLENGES & SOLUTIONS

1. Resolving tenant, branding, and session state before first paint. Because one deployment serves many schools, the app can't render anything — not even the login screen — until it knows which school it's serving, what that school's branding and active features are, and whether the visitor already has a valid session. I solved this by consolidating school detection, feature-flag resolution, and session lookup into a single upfront RPC call, gating the entire route tree behind one loading/error state so there's no flash of the wrong school or an unstyled login page.

2. Keeping role-based access control consistent across a very large route surface. With five roles, four permission-gated admin sub-areas, and well over 100 routes, letting authorization logic drift between pages was a real risk. I addressed the navigation side by driving all menu rendering from one central configuration (NAV_STRUCTURE) filtered by role and permission at render time, and addressed the routing side by repeating a role check with a redirect fallback at every protected route — a pattern that's consistent today but that I'd refactor into a single reusable route-guard component in a next iteration to remove the repetition.

3. Preventing data loss during bulk score entry. Teachers enter scores for many students against a given assessment in one sitting, and losing that work to an accidental tab close or navigation was the biggest usability risk in that flow. I built a local-state model that diffs against the last-saved scores, tracks a hasChanges flag, and hooks the browser's beforeunload event to warn before an accidental exit — while saving only the changed values back to Supabase rather than re-writing the entire score set.

4. Building a PDF result-card system that supports dozens of regional templates without code duplication. The requirement to produce country/state-specific result cards (all 36 Nigerian states, plus Ghana, Kenya, etc.) could have led to a sprawling set of nearly identical components. Instead, I designed a factory pattern with a shared rendering pipeline: layout, header, footer, and grade tables are driven by a configuration object per region. This keeps the core rendering logic in one place while allowing per‑region overrides for grading scales, subject lists, and branding.

5. Running a live product through a structural migration without breaking existing schools. The codebase currently carries both "legacy" and "_new" versions of the admin and teacher modules side by side, and mixes JavaScript with an incoming TypeScript layer. This wasn't an accident of scope creep — it's the visible trace of restructuring an in-use application incrementally, keeping the old routes functional for schools already depending on them while the newer implementation matured alongside it.
